## Overview
For Version 2.0 of SABLE, the main improvements should focus on reliability, debuggability, communication stability, and better sensor integration. The current prototype successfully demonstrated the major subsystems: drivetrain, manipulator arm, sound sensor, camera, HMI, and Wi-Fi connection. However, the project summary notes that several team members had to revise and reorder PCBs, which shows that the next version should be designed with easier testing, clearer diagnostics, and more robust subsystem integration in mind.

The existing block and process diagrams show that SABLE uses a daisy-chained UART system where messages travel between the Wi-Fi board, arm board, locomotion board, audio board, camera board, and HMI board. This modular design is useful because each subsystem can be developed separately, but it also creates a weakness: if one board fails, disconnects, or mishandles a message, the rest of the chain can lose communication. For Version 2.0, the communication system should be improved so each board can report its status, confirm received messages, and identify faults before the operator loses control of the robot.


## Future Improvements

One major improvement for Version 2.0 would be a stronger communication protocol. The current message structure uses start bytes, source ID, destination ID, a variable message section, and end bytes. This is a good starting point, but the protocol should be updated to include a message length byte, checksum or CRC byte, message counter, and acknowledgment response. The length byte would make it easier for each board to know how much data to expect. The checksum would help detect corrupted UART data. A message counter would help identify dropped or repeated messages. An acknowledgment message would let the sender know that the command was received and processed. This would make commands like movement, arm position, speaker playback, and stream telemetry more dependable.

Version 2.0 should also improve debuggability. The project requirements already mention that the HMI should be able to view sensor data, modify setpoints, and toggle GPIO debug pins on all subsystems. In the next version, each subsystem should have built-in debug features such as status LEDs, test pads for UART and power rails, serial debug headers, and a standard “heartbeat” message sent once per second. The HMI and web interface should display whether each board is online, what voltage it is receiving, whether it has recent communication errors, and what command it last processed. This would make troubleshooting much easier during testing because the team could quickly identify whether the issue is power, firmware, wiring, or protocol related.

Another improvement would be adding more reliable power monitoring. Since SABLE is intended for search and rescue or hazardous environments, it needs to operate reliably while driving over rough terrain. The requirements already emphasize stability, rough-ground movement, wireless control, video, distance sensing, and fast charging. Version 2.0 should include battery voltage sensing, current monitoring, brownout detection, and regulated power status reporting. Each board could report whether its 3.3V rail is within range. This would help prevent random resets, weak wireless performance, and camera failures caused by unstable power.

The camera subsystem should also be improved. The current requirements include stable video while moving and live video output. Version 2.0 could add camera telemetry such as frame rate, resolution, dropped frame count, and stream status. The camera board could send short UART messages to the HMI and Wi-Fi subsystem so the operator knows whether the video feed is active. A future version could also include image stabilization, a better camera mount, a wide-angle lens, or low-light LEDs to improve visibility in dark or dusty environments.

For new functions, Version 2.0 should include autonomous safety behaviors. For example, if communication is lost, the robot should stop moving automatically. If the distance sensors detect an obstacle, the drivetrain should slow down or stop before impact. If the robot flips over or tilts too far, the arm subsystem could attempt a self-righting routine. These features support the original search and rescue goal because the robot may be used in dangerous environments where the operator cannot physically reach it.

Overall, Version 2.0 should keep the same modular subsystem layout shown in the block diagram, but improve the software and hardware around it. The biggest upgrades should be a more fault-tolerant UART protocol, better HMI/web diagnostics, power monitoring, camera telemetry, and safety fallback functions. These changes would make SABLE more reliable, easier to debug, and better suited for real exploration or rescue use.
